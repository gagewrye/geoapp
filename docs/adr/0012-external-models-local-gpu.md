# 0012: Running large external models on the user's GPU

**Status:** Accepted (Gage, 2026-10-26). Option (ii) becomes spec 006, built after spec 004; change detection and prediction move to specs 007 and 008. Shelved by spec 013 (2026-10-28), except option (iii), importing a classified GeoTIFF, which holds. ADR 0031 (Gage, 2026-10-31) takes up option (i), onnxruntime-web on WebGPU, for one small model: spec 046's SAM 2.1 Tiny.

**Context:** Gage has a large model that shouldn't run on CPU. User data never leaves the device (CLAUDE.md), so only local options count. Checked 2026-10-26. (i) **onnxruntime-web 1.31.1** (MIT, npm `latest`) with the WebGPU EP (`onnxruntime-web/webgpu`, `executionProviders: ['webgpu']`, [docs](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html)). One protobuf is capped at 2 GB, and even with external data a model can't exceed 4 GB (wasm32) ([large models](https://onnxruntime.ai/docs/tutorials/web/large-models.html)). WebGPU's default limits are `maxBufferSize` 256 MiB and `maxStorageBufferBindingSize` 128 MiB unless the adapter grants more ([W3C](https://www.w3.org/TR/webgpu/)). The EP lists about 108 ops, including Conv, Resize, LayerNormalization and MultiHeadAttention; there's no conv3d, and attention masks aren't implemented ([ops](https://github.com/microsoft/onnxruntime/blob/main/js/web/docs/webgpu-operators.md)). Unsupported nodes fall back to the CPU (wasm) EP ([EPs](https://onnxruntime.ai/docs/execution-providers/)). WebGPU is shipped in Chromium 113+ on Windows, macOS and ChromeOS, but on Linux only from 144 (Intel Gen12+) and 147 (NVIDIA driver 535.183+, Wayland). Firefox ships it from 141 on Windows and 145/147 on Apple-silicon macOS, and Linux is nightly only; Safari has it from 26 ([status, edited 2026-10-02](https://github.com/gpuweb/gpuweb/wiki/implementation-status)). The model must also be exported to ONNX. (ii) **A local inference server** that the user runs with their own framework and GPU, bound to 127.0.0.1. `localhost` and 127.0.0.0/8 are potentially trustworthy ([MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)), so Chrome and Firefox don't block them as mixed content from our https origin. Safari still blocks them (WebKit bug 171934 is open; its page returned 503, so this is untested). Chrome 142+ asks the user for Local Network Access before a public site can reach loopback ([Chrome](https://developer.chrome.com/blog/local-network-access)). The server must answer CORS preflights for our origin. (iii) **No code:** run the model anywhere on the machine and import its classified GeoTIFF through spec 004 (a).

**Decision:** (iii) now, because it works as soon as spec 004 ships, and (ii) as spec 006. The app never scans ports: the user enters the server URL (default `http://127.0.0.1:<port>`). The server prints a random token, which the app sends as `Authorization: Bearer`, so other sites that get the Local Network Access grant still can't use it. CORS allows only the app's origin. The app sends imagery tiles and gets back class tiles (plus optional max probability), which go through spec 004's seeding path, including its Merge/Replace choice and imagery-nodata mask. (i) is deferred: the 4 GB and buffer limits, the ONNX export step and patchy Linux WebGPU fit a big model badly, though it could later run small ONNX models with nothing to install.

**Consequences:** (iii) adds nothing. (ii) adds no browser dependency, but the user installs and runs a program, and its spec defines a small HTTP protocol and probably a reference server script that we don't host. It works in Chrome and Edge (after the prompt) and in Firefox, but not in Safari. Requests go only to the configured loopback URL, so the privacy criteria allow exactly that URL. (i) would add onnxruntime-web and its wasm files as a dependency under its own ADR.
