# 0010: Painted labels as sparse in-memory tiles, per-tile overlays, run-length JSON files

**Status:** Proposed

**Context:** Painted labels live on the source raster's pixel grid (spec 003). A dense Uint8 label raster for a 20k x 20k image is 400 MB, and CLAUDE.md forbids holding a full raster in memory. Storage options: (a) a sparse in-memory map of 256x256 Uint8 tiles with a cap; (b) OPFS-backed tiles, which are unbounded but make painting async and need more code. For display, a single overlay at preview resolution (at most 1024 px) would hide fine labels on a large raster, since decimation can skip a 1 px dab entirely. maplibre-gl 6.16.0 `src/source/canvas_source.ts`: with `animate: false`, the canvas is re-uploaded only on resize or while playing (`prepare`), and `pause()` runs `prepare` once if playing. Axis-aligned Mercator rectangles are the safe case for image placement (ADR 0002). For saved files, ADR 0001's writer is uncompressed and writes every tile, so a label GeoTIFF would be full raster size and mostly zeros, and its GDAL_NODATA "255" collides with class 255.

**Decision:** Option (a), with `MAX_LABEL_TILES` = 256 (16 MiB). Each labelled tile gets its own canvas source, warped onto an axis-aligned Mercator grid at tile resolution, and `map/` calls `play()` then `pause()` after each redraw. Labels are saved as JSON with per-tile run-length runs.

**Consequences:** No new dependency. Memory stays bounded at about 16 MiB of labels plus up to 256 overlay canvases of about 256 KiB each, plus their GPU textures and up to 256 extra map layers. A dab that would need tile 257 is refused with a message. Label files can't be opened in GIS tools; a GeoTIFF export can come after compression lands (ADR 0001). Raising the cap, or moving to OPFS (option b), changes only the store.
